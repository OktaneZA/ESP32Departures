# Departure Buddy — web configurator

**Live at <https://wonderful-pond-001d18503.7.azurestaticapps.net>**

A static page that configures a board: pick your station, stop and pier, choose
colours and timings, preview the result, then send it to the device over USB
from the browser — or download a settings file for the Windows installer.

There is **no backend**. Every API it needs is CORS-open, so the whole thing is
plain static files.

## Run it locally

```bash
python web/build-firmware.py        # stage firmware + write its manifest
cd web
python -m http.server 8765 --bind 127.0.0.1
```

Then open <http://127.0.0.1:8765> in **Chrome or Edge**.

Two things to know:

- **Web Serial needs a secure context.** `127.0.0.1` counts as one, so plain
  HTTP is fine locally — but opening `index.html` as a `file://` path is not,
  and the Connect button will not appear.
- `build-firmware.py` is only needed for the **flashing** path. The configurator
  itself works without it; it just cannot put firmware on a blank board.

Firefox and Safari have no Web Serial, so they get the downloadable settings
file instead, to be dropped onto the
[Windows installer](https://github.com/OktaneZA/ESP32Departures/releases/latest). The page detects this and says so.

## Deploy to Azure Static Web Apps

Azure serves it over HTTPS automatically, which browser flashing requires.
The free tier is enough — the site is about 1.2 MB.

**One-time setup.** With the [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli)
installed:

```bash
az login

az group create \
  --name departure-buddy \
  --location westeurope

# Static Web Apps runs in a limited set of regions; westeurope is the closest
# to the UK. Deployment source is "Other" because this repo brings its own
# workflow (it has to stage the firmware first).
az staticwebapp create \
  --name departure-buddy \
  --resource-group departure-buddy \
  --location westeurope \
  --sku Free

# The deployment token the GitHub workflow authenticates with.
az staticwebapp secrets list \
  --name departure-buddy \
  --resource-group departure-buddy \
  --query "properties.apiKey" -o tsv
```

Copy that token into the repo at **Settings → Secrets and variables → Actions →
New repository secret**, named exactly:

```
AZURE_STATIC_WEB_APPS_API_TOKEN
```

Push to `main` (or run *Publish configurator (Azure)* from the Actions tab) and
it deploys. Find the URL with:

```bash
az staticwebapp show --name departure-buddy --resource-group departure-buddy \
  --query defaultHostname -o tsv
```

### What the Azure config does

`staticwebapp.config.json` sets the MIME type for `.bin` so the firmware images
download as binaries, and marks the manifest and images `no-cache` so a board is
never flashed with a stale build.

It deliberately sets **no `navigationFallback` and no 404 rewrite**. This is a
plain multi-file site, not a client-routed SPA: a missing firmware file must
return a real 404 so the page can say "no firmware published here", rather than
being handed `index.html` and failing to parse it as JSON.

## Deploy to GitHub Pages instead

`.github/workflows/pages.yml` does the same job. It needs Pages enabling once by
hand — **Settings → Pages → Build and deployment → Source: GitHub Actions** —
and will fail on every push until you do. If you are using Azure, delete that
workflow.

## Layout

| Path | What it is |
|---|---|
| `index.html` | the form, preview and installer UI |
| `js/config.js` | config model, the `mode` set, RGB565 colour maths |
| `js/api.js` | TfL / postcode / rail lookups — ports of `installer.py` |
| `js/serial.js` | provisioning over Web Serial (`PING`/`CFG`/`COMMIT`) |
| `js/flash.js` | flashing a blank board via esptool-js |
| `js/app.js` | UI wiring, pickers, preview |
| `data/stations.json` | 2,608 UK stations: CRS, name, position |
| `vendor/` | esptool-js, vendored byte-identical to upstream |
| `firmware/` | generated by `build-firmware.py`, not tracked |
